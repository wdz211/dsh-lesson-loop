# dsh-lesson-loop

> A closed loop that makes an agent actually learn from its own mistakes: capture → judge → ledger → consolidate → repair → audit.

## 这是什么

大多数 agent 都说自己"会从错误里学习"，实际做法是把几条教训写进一段自由文本的「注意事项」，
然后指望下一次它自己想起来读。这条路注定失败：靠自觉的记录必然漏，而自由文本没法统计
「同一个坑到底咬了几次」。

这条链路换了个做法——**把错误变成有主键的数据**。

执行过程中冒出来的问题被压成一条原始记录丢进输入口；一个定时整理器把它聚成条目、算出等级、
写进账本；等级够了的条目进修复队列，被真正动手修（或者留下"试过但没修好"的痕迹）；长期不再
出现的自动归档；最后有一个只读面板把账本摊开给人看。中间每一步都不需要有人记得去做。

它真正的产出不是"一份错误清单"，而是**一个可证伪的顽固度指标**：一个缺陷出现三次，说明前两次的
修法都没覆盖住；修完标 fixed 之后又出现，说明"以为修好了"是假的。这两个信号，自由文本笔记
永远给不出来。

## 为什么值得看

设计上真正非显然的几个决定，每个都在 ARCHITECTURE 里有单独一节讲清楚它当初踩了什么坑：

1. **采集与判断分离**：写入零模型调用，贵的判断攒到定时整理里一次做掉 —— §3.1
2. **等级 = 出现次数，不是主观打分**；而等级只管修复优先级，**不管归档寿命** —— §4.1
3. **指纹压掉路径、数字、引号、时间**，复发是给同一条账加一次，不是新开一条 —— §4.2
4. **输入口允许有多个写者，账本只允许一个写者** —— 这条边界是整条链路能同时被两个插件喂养的原因 —— §4.3
5. **修不好也必须留痕**：连修三次不愈标"硬骨头"，但依然继续修，不是停手 —— §3.5
6. **「0 条」也要落一行心跳**：模型说"没问题"和"根本没看"在输出上长得一模一样 —— §3.1

## 一条记录长什么样

输入口里一行就是一条（示意，字段是真实的，内容是虚构的中性例子）：

```json
{"at":"<ISO 时间>","type":"issue","kind":"bug","title":"写后未读回验证",
 "detail":"改完配置只看了退出码，没读回文件确认真的生效","anchor":"写后未读回验证",
 "session":"<某个会话>","seq":42,"source":"manual"}
```

整理之后它会变成账本里的一条：有 `id`、有 `fingerprint`、有 `level`、有 `status`，
`occurrences` 里攒着每一次复发的原文与位置。**同一个骨架再出现一次，不是新增一条，
而是给这一条 +1**。

## 它能回答的三个问题

1. 「这个坑以前咬过我吗？咬过几次？」
2. 「上次修的时候是怎么试的、为什么没成？」（修复简报里带着往次做法，避免重复死路）
3. 「我标了已修的东西，有多少又回来了？」（`status` 从 `fixed` 翻成 `recurred` 的那些）

第三个问题是这套机制最尖锐的地方：它专门揪"很多人以为处理完了、其实还活着"的问题。

## 它刻意不做的事

- **不自动改代码。** 修复队列只负责挑出该修哪条、给一份带证据的简报；动手是人或派出去的执行器，
  修完再回来落账。说清这一点，才不会变成"看起来在自动修"。
- **不评价严重程度。** 等级只有"出现次数"这一个来源，没有主观打分——主观打分会让"顽固"
  变成"我觉得顽固"。
- **不做常驻监听。** 没有 watcher、没有全局 debounce 计时器，整理由定时任务触发。

## 怎么读这三份文档

| 文档 | 回答什么问题 |

| `COMPONENTS.md` | 每个模块的职责与仓库地址，以及哪个能点开、哪个还没公开 |

本仓是**纯文档仓**，不含源码：代码留在各自的单插件仓里，这里只负责讲清楚"整条链路怎么跑、哪一块在哪"。
这条链路全部自研，没有上游第三方模块，因此没有 `UPSTREAM.md`。

## 一个必须先记住的结论

归档口径是**一律 7 天**没再出现即归档，与等级无关（`ARCHIVE_DAYS_BY_LEVEL = {1: 7, 2: 7, 3: 7}`）。
任何"一级 30 天 / 二级 60 天 / 三级 180 天"的说法都是读到了废弃的旧注释 —— 详见 §4.1。
这是这条链路里最容易被人抄错的一处，所以单独在 README 里再写一遍。
